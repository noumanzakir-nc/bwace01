# Integration Test Instructions — BW-ACE

## Purpose

BW-ACE is a two-unit monolith (`unit-of-work.md` §1) with exactly one crossing point: Unit 2 calls Unit 1's `AssessmentService` (`assess`, `compute_base`, `apply_config`, `compare`) and Unit 1's `loader`/`export` functions, and receives `AssessmentResult` in return. There is no network boundary, no separate deployable, and no service contract beyond a Python function signature — so "integration testing" here means confirming that boundary is actually exercised correctly end to end, not merely that each unit passes its own tests in isolation.

## Test Scenarios

### Scenario 1 — Unit 2 consumes a real Unit 1 result through every view
- **Description**: every Unit 2 view is rendered against a real `AssessmentResult` produced by the real Unit 1 pipeline (not a mock or fixture), and the KPI figures displayed are checked against Unit 1's independently-verified reference numbers.
- **Setup**: none beyond the installed package — the bundled dataset is the fixture.
- **Test steps**: `tests/app/test_smoke_views.py::test_dashboard_kpis_match_reference` and `test_every_view_renders_without_error`, executed via `pytest tests/app`.
- **Expected results**: KPI strip reads 22 objects, 604 GB, 21 GB reclaimable; all five views render with zero exceptions and zero error boxes.
- **Already executed**: yes, as part of Unit 2's own test suite. Re-run here as an integration check because it is the boundary crossing, not because it is new.
- **Cleanup**: none — read-only.

### Scenario 2 — A threshold change propagates from Unit 2's control through Unit 1's engine back into Unit 2's rendering
- **Description**: confirms the full round trip — a UI-level interaction actually reaches `apply_config` and the result actually changes what renders — rather than each half being correct in isolation but disconnected.
- **Setup**: none.
- **Test steps**: `tests/app/test_smoke_views.py::test_threshold_change_recomputes_without_error` moves the Effort slider via the real widget and reruns.
- **Expected results**: no exception; by construction (`FI100GC` flips category at Effort 66, verified independently in both `tests/engine/test_reference_dataset.py::test_fi100gc_flips_at_effort_66` and used as the concrete example throughout the functional design), a real classification change is known to occur on this exact interaction.
- **Cleanup**: none.

### Scenario 3 — Scenario comparison round-trips through `compare`
- **Description**: Unit 2's Scenario Compare view calls Unit 1's `service.compare`, which itself calls `compute_base` once and `apply_config` twice — this is the one Unit 1 function whose entire purpose is to be called from Unit 2's UI layer with live user input.
- **Setup**: none.
- **Test steps**: `tests/app/test_smoke_views.py::test_scenario_save_and_compare_flow` — saves two scenarios via the real save button, selects both via the real dropdowns, and asserts no exception.
- **Expected results**: no exception; the changed-object table renders (verified separately at the engine level that `FI100GC` is the one object that changes between the two saved configurations).
- **Cleanup**: none — session state is discarded when the test's `AppTest` instance goes out of scope.

### Scenario 4 — Export functions consume a live result, not a fixture
- **Description**: `main.py`'s download buttons call Unit 1's `export.classification_csv` / `wave_recommendation_json` directly on the `result` computed for the current render, rather than on a pre-serialised sample.
- **Setup**: none.
- **Test steps**: exercised indirectly by `tests/engine/test_export.py` and `test_reference_dataset.py::test_exports_contain_22_rows_and_embed_config`, which call the same functions Unit 2 calls, against the same `AssessmentResult` shape. A direct UI-level `AppTest` click on `download_button` is not performed, because Streamlit's `AppTest` harness does not execute the browser-side file-save action — the data passed to `st.download_button` is generated by the same code path already covered.
- **Expected results**: CSV has 22 data rows; JSON contains configuration values matching what produced it.
- **Cleanup**: none.

## Setup Integration Test Environment

No services to start — this is a single-process application with no database and no network dependency. The "environment" is the installed `bwace` package plus the bundled `data/` files, both already present after Build Instructions step 2.

## What Makes This Integration Testing Rather Than Duplicate Unit Testing

Unit 1's tests construct `Landscape` and configuration objects directly and call engine functions. Unit 2's tests in this file drive the **same underlying computation** but exclusively through Unit 2's real UI widgets and Unit 1's real public service functions — never by importing an engine internal directly into a Unit 2 test. This is what confirms the two units are actually wired together as designed (`services.md` §2.3), not merely that each independently does the right thing.
